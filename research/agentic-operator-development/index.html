01

核心判断

UX 的交付重心应转向“开发者如何委托任务、检查结果、介入例外，并把有效方法留给团队”。成功的体验可以让用户完全不打开可视化。

需要同时接受两个判断：常规界面设计与实现的稀缺性确实下降，不能保证 UX 岗位数量不变；但用户少操作界面，不等于结果验收、异常恢复和多人协作自动变简单。新机会必须用任务结果证明，不能仅靠扩大 UX 的定义来主张价值。

“编码与精度归 Agent，性能归可视化”可以描述局部现状，不能作为稳定边界。更合适的分界是：目标是否明确、结果能否验证、证据是否充分、试错成本是否可接受、任务是否包含需要人选择的取舍。同一项精度或性能任务可以在不同协作模式间切换。

04

协作方式由任务条件决定

  • 直接委托：目标清楚、验收器可靠、反馈成本低。Agent 执行到验收，用户默认只看结果与适用范围。
  • 批次检查：任务长、资源有限，但阶段结果可判断。按实验批次报告，而非每个 tool call 打断用户。
  • 共同探索：目标有取舍、证据存在竞争解释。人通过比较、圈选、排除假设参与，Agent 补证据和执行实验。
  • 人工接管：观察能力缺失、验证不可用或任务越界。交付检查点、已排除路径、待补信息，允许接管后继续委托。

默认模式可随项目和用户变化；同一任务也会切换。切换依据应是可观察事件，例如验证失败、预算耗尽或需要修改目标，而非未经校准的“Agent 自信度 90%”。不把每次只读查询、常规生成或可撤销实验都设计为审批。

优化“场景—数据—可视化—Agent 调用”关系

建议主线：

Agent、工具与可视化围绕同一份任务和证据工作，而不是顺序串接的步骤。

层 需要定义的契约 UX 参与点 合作责任
目标与验收 优化谁、什么输入、怎样算成功、资源预算 意图澄清、默认值、约束冲突表达 算子/模型专家确认有效标准
证据与语义 源码版本、运行身份、设备环境、采集范围、单位与指标定义、缺失项 用户能否确认“正在讨论同一个对象” 数据与工具工程提供权威计算和关联
假设与实验 观察事实、候选解释、反证、改动、预测与测量分离 比较与决策、提出反例、选择补采样 领域专家校验诊断逻辑
执行与控制 Skill 输入输出、前置条件、停止/恢复、动作范围 进度、失败恢复、介入时机 Agent/平台团队实现与保障
人的表达与反馈 摘要、表格、图、代码 diff、圈选/批注 让当前判断所需证据容易进入和返回 前端/可视化团队实现

示例链路：用户说“解释这一段等待” → 视图选择转成运行身份、对象集合和时间范围 → Agent 查询结构化数据 → 工具返回指标及来源 → Agent 提出假设和补采集动作 → 图中定位证据 → 用户修正范围或提交实验 → 复跑结果进入同一任务。

关键约束：UI 与 Agent 尽量消费同一份版本化计算结果；不要分别从原始 JSON 临时猜指标定义。图上选区还要保留边界外依赖的补查能力，避免把屏幕裁剪误作诊断范围。

06

可视化设计分类、组合与删减标准

6.1 分类层次：让名称直接提示视觉组织方式

本节依据用户对分类角度的澄清形成设计工作框架：分类应帮助设计师联想到“信息怎么摆、关系怎么画、注意力怎么引导”。它属于本研究的设计归纳，不是外部标准或已经验证完备的分类体系。

区分四个维度，避免把它们混成一组类别：

维度 回答的问题 示例
设计分类 如何组织视觉表达，让用户看清当前问题？ 表达范围、检查关系、候选比较
表现形式 用什么图形或信息载体承载？ 卡片、表格、网格、泳道、热力图
交互方式 用户如何操作表达、补充意图或继续行动？ 筛选、圈选、标注、联动、跳转、向 Agent 提问
使用场景 在什么工作情境中使用？ 设计、开发、精度调试、性能调优、例外接管、交付协作

“表达范围”指表达数据覆盖、计算、影响、调度、并行或资源共享等边界。用户向 Agent 转述某个选区属于交互方式，可配置在各种设计分类之上。“例外接管”和“交付协作”属于场景，不与设计分类并列。

6.2 七类可组合的可视化设计方式

设计分类 可以联想到的视觉组织方式 典型表达与设计重点
对象概览类 卡片、分区、关键值、标签、摘要 用算子规格卡等表达对象是什么、关键约束及支持边界，形成可快速扫读的整体
表达范围类 边界框、分区、包围、覆盖、嵌套、共享区域 用 Tile 网格、分块矩阵、内存层级图等明确数据覆盖、计算分块、资源共享或作用边界
检查关系类 连线、邻接、层级、映射、对齐、关联高亮 用血缘、层级与映射表达来源、依赖、归属、对应和搬运关系
定位重点类 排序、色阶、峰谷、离群点、局部放大 用 Top-K 表、误差分布图、瓶颈热力图突出值得关注的对象、区域和异常模式
候选比较类 并排、叠加、共同基线、差值、对应项对齐 将方案、版本或参数候选置于可比条件下，让差异与取舍直接可见
过程追踪类 时间轴、泳道、阶段、轨迹、事件标记 呈现运行或开发过程中的先后、持续、重叠、等待与转折
归因解释类 结论与证据配对、解释分支、支持与反证并置 用瓶颈归因卡等组织现象、可能原因、证据和验证状态，形成可检查的解释结构

这些类别不要求互斥。同一载体可以组合多类设计方式；分类依据是当前表达如何组织，而不是图表名称。“候选比较类”没有专属图形，卡片、表格、泳道和矩阵都可以采用这种组织方式。

6.3 十一种可视化的分类映射

可视化形式 基础设计分类 可叠加的设计分类与条件
误差分布图 定位重点类 统一尺度叠加不同版本时属于候选比较；明确标出容差区间时也表达范围
Top-K 表 定位重点类 若行代表备选方案，且提供一致评估维度与取舍信息，也属于候选比较；只有排名不能代表整体分布
泳道片段 过程追踪类 加入依赖线时检查关系；标出调度、并行分组时表达范围；对齐两个版本时进行候选比较
瓶颈归因卡 归因解释类 并置竞争解释及其证据时进行候选比较；若仅显示结论标签与关键值，则只承担对象概览
算子规格卡 对象概览类 用分区或边界明确支持的输入、计算覆盖等范围时，也属于表达范围；可编辑或可发送给 Agent 属于交互配置
Tile 网格 表达范围类 加入 Tile 与核心/任务的映射时检查关系；叠加耗时色阶时定位重点；并排划分策略时进行候选比较
分块矩阵 表达范围类 加入块间计算、访问或维度对应时检查关系；并排分块方案时进行候选比较
内存层级图 检查关系类 表达归属、层级与搬运路径；用嵌套区域表示共享或可访问边界时表达范围；叠加带宽、容量压力时定位重点
瓶颈热力图 定位重点类 保持尺度与对象对应后比较版本时属于候选比较；只有热点颜色不能证明瓶颈原因
算子血缘图 检查关系类 标明有依据的变更影响对象时表达范围；加入派生阶段或版本演进时进行过程追踪
变更时间线 过程追踪类 关联改动与实验结果时检查关系；对齐多个版本的可比结果时进行候选比较

几组边界需要保留：

  • Tile 网格与分块矩阵可能是同一种设计分类的不同载体。前者常强调 Tile 单元与任务映射，后者常强调数据维度和分块关系；以实际内容判断，不按名称强行分开。
  • 泳道片段呈现一次运行内部的执行过程；变更时间线呈现开发过程中的方案与实验演进。两者同属过程追踪，但时间语义不同。
  • 算子血缘图表达派生与来源，执行依赖图表达等待与并行条件。来源关系不能直接当作调度依赖。
  • 误差分布、泳道和热力图可以揭示模式；归因解释仍需区分观察、候选原因和已验证结论，不能把空间或时间相关性直接写成因果。

6.4 从分类到具体设计

推荐推导顺序：

当前需要用户看清什么 → 选择设计分类 → 确定视觉组织方式 → 选择图表载体 → 配置交互

例如，比较两种分块方案：先选择候选比较类，再确定并排、对应位置对齐与共同评价尺度，随后使用两张分块矩阵，最后配置联动、圈选和 Agent 提问。不要先决定画矩阵，再寻找它能回答的问题。

使用场景可组合多类设计：例外接管可能需要对象概览、过程追踪与归因解释；交付协作可能需要规格概览、关系检查与候选比较。向 Agent 提问可以配置在任何类别上，其上下文绑定遵循第 5 节的共同证据要求。

6.5 展示与删减标准

直接返回一个通过验证的结果时，可以零图表；简单比较用表格即可；需要关系推理时再使用泳道、依赖图或误差图。按需打开不等于每次生成一个风格全新的工作台，应保留稳定图形语义和对象身份。

可视化触发规则是研究启发式：只有预期能降低遗漏、错误判断或沟通成本，并超过读图和打断成本时才展示。检验方法是与纯 Agent 摘要对照；如果加图没有改善判断和任务结果，就移除该图。

07

候选体验策略与具体机会

候选策略：让开发者以可验证的结果推进算子交付，并在需要时有效介入。

以下按体验原则组织，不构成正式设计 registry；作用机制与收益尚待验证。

方向与概括性收益 具体问题 设计选择 作用机制 可验证的具体收益
明确委托边界：减少任务返工 自然语言遗漏 shape、设备、性能目标 从工程提取约束，只询问缺失或冲突项 把含混愿望转成可执行验收条件 因目标遗漏而重开任务次数减少
同上 单个样例通过被误当全范围通过 结果携带已验证与未验证范围 在接受时暴露覆盖边界 错误接受未覆盖输入的比例下降
保持证据一致：降低核对成本 人与 Agent 对时间、对象、版本理解不同 跨摘要、图、代码保留同一对象与口径 减少重新寻找与手工换算 证据定位耗时和错配率下降
同上 性能建议从观察直接跳到根因 分开表达事实、竞争解释和区分实验 用户能检查建议凭据并推翻假设 无证据试改和重复失败减少
让介入发生在必要处：降低监督负担 一直聊天或一直守着运行 按约束变化、失败和预算节点请求介入 日常步骤自动推进，关键选择及时暴露 总监督时间下降且误接受不增加
同上 接管时只有长聊天历史 交付可继续的检查点与失败摘要 让用户从当前问题接续而不是重新诊断 接管到下一次有效行动的时间缩短
让个人经验进入团队：减少重复探索 定制脚本只能原作者使用 保存输入范围、计算口径、样例与回归条件 方法连同边界一起复用 跨人复现成功率提高
同上 用户改界面后语义悄然变化 允许视图组合自由，保持指标和对象契约稳定 定制不会破坏团队共同理解 定制后回归失败与支持成本下降
08

三个用于验证机会的场景脚本

均为构造场景，不是已有产品能力或实测案例。

A. 常规算子生成：让界面退出主流程

用户提交算子语义与目标环境 → Agent 提取支持范围和参考实现 → 在既定范围生成代码、构建、验证 → 返回可运行实现、验证范围和复现入口。全部通过时不弹出大图；约束冲突时才显示选择。

检验：任务完成时间是否缩短，用户是否理解未覆盖范围；不能仅统计生成代码速度。

B. 精度难例：从通过率转向首次异常与适用边界

常规输入通过，特殊 shape 或输入分布失败 → Agent 最小化失败样本并比较中间结果 → 默认给出首次差异和候选解释 → 用户需要判断误差扩散或业务容差时，展开误差分布/层间对比 → 修复后跑独立回归。

检验：错误接受率、定位时间与修复后回归表现。容差属于验收条件，不允许为了通过而静默放宽；golden 与实现必须避免共享同一错误假设。

C. 性能优化：用最小实验辨别原因

Agent 在运行中发现一段空闲 → 提出依赖等待和工作划分不均等竞争解释 → 获取区别这些解释的依赖、时间与统计证据 → 用户按需圈选范围、排除不符合业务条件的实验 → 在预算内试改并复测精度与性能 → 返回单算子结果和模型端到端影响。

检验：确定有效优化所需实验次数、设备耗时、监督时间以及错误归因。图形帮助发现关系，不能把时间相关性直接写成因果。

09

半年路线：2026-09 至 2027-03

优先交付可验证的工作流切片，暂不建设覆盖所有场景的大平台。

时间 UX 具体工作 可评审交付 进入下一步的依据
0–1 月 观察真实任务，记录委托、返工、介入与交接 建议招募 6–10 位跨角色参与者、采集 12–20 个任务；规模仅用于定性探索 找到重复且高成本断点；不能外推人口比例
1–3 月 联合工程定义任务验收与证据一致性；试验结果优先输出 可验收任务摘要、可追溯结果、必要介入和恢复原型 在固定版本与工具能力下，与现有流程比较任务效果
3–6 月 跑通常规生成、精度异常、性能实验三类任务 真实工作流试点、评测集、用户验证报告 常规任务少干预；复杂任务降低错判与接管成本；无收益则删减交互

优先级：第一优先是验收边界、共享证据和结果回溯；第二优先是失败接管与候选比较；第三优先是动态可视化生成和大范围 Toolkit 自定制。优先级来自失败成本与可验证性判断，尚没有 ROI 实测。

如果资源只能支持一个试点，选择“已有 Agent 性能分析与泳道结果对齐，并完成一次可比实验”。它有历史反馈、现有视图和已有设计基础；同时用一个常规代码生成任务检验“无需可视化”的边界，防止只研究最适合图的样本。

10

一年路线：2027-03 至 2027-09

在半年试点有收益后，将局部方案固化为跨任务能力：

  • 可复用任务模板：描述目标、输入、范围、验收、预算、交付和失败出口；支持不同 Agent 宿主。
  • 共同证据契约：让源码、测试、运行、指标与 UI/MCP 使用一致身份和定义。UX 定义人必须理解的语义，工程实现与校验。
  • 可定制的工具基础：把布局、筛选、组合等个人偏好开放给用户；对指标语义、来源、兼容性和回归条件保持稳定约束。
  • 真实任务评测与失败知识：记录什么用户在什么条件下成功或失败，把新模型、Skill、界面改动放到同一验证集比较。

规划不是能力预测。若 Agent 提升更快，将更多资源投向验收、跨任务控制和方法复用；若 Agent 提升较慢，继续投入专家诊断与快速接管。共同投资是任务语义、可靠证据和评测，避免押注某一代模型的弱点。

UX 护城河与团队职责

资产 为什么可能积累优势 防止自我安慰的要求
真实任务与失败案例库 外部模型不知道本团队的目标冲突、失败代价、环境限制和协作断点 持续接触用户，提供可复现案例并保持更新
领域判断模型 明确何时能信、何时补证据、何时做实验、何时停止 与专家共同验证，落实到产品状态和验收条件
人与 Agent 的协作语义 把目标、对象、证据、动作与结果连接起来，可跨界面和宿主复用 必须进入工程契约，不能只留在设计稿
用户结果评测体系 判断一次改动是否让任务更容易成功，包含监督与恢复成本 评测真实任务，保留负面结果并影响优先级

这些是跨职能资产，UX 没有天然专属权。UX 要用研究、流程推导、原型和评估持续贡献，工程与领域专家共同建设。Prompt、Skill 数量、图表数量、某套视觉风格和“只有设计师会改界面”都难成为持久壁垒。

职责建议：UX 主导任务研究、协作体验、信息语义与用户效果评估；领域专家主导数学/精度/性能有效性；工程主导运行时、数据计算、工具实现与可靠性；产品负责人协调业务目标和资源。不要把全部 Agent 基础设施改名为 UX 工作。

设计师应补足：读代码与运行产物的能力、测试与指标常识、Skill/MCP 输入输出理解、可运行原型与评测能力。深度以能发现断点并与工程共同验证为准，不要求人人成为 kernel 专家。

衡量方式与下一步验证

核心指标：达到可交付结果所需的总时间，在明确的错误接受率约束下。 分开记录用户主动工作、监督检查、设备执行与等待时间，避免只优化某一项。

配套指标：一次验收通过率、错误接受率、证据定位时间、接管恢复时间、无效实验与设备成本、跨人复现率、端到端模型收益。打开图次数、聊天轮数和 Agent 调用数仅作诊断变量，不能直接当成功指标。

对比条件：传统工具流程、Agent 摘要流程、Agent 加按需证据交互。按用户熟练度和任务复杂度分层；对比时固定模型、工具版本、数据与验收规则，尽量交叉安排任务顺序。分别判断常规、难例与例外任务，不用总体平均数掩盖差异。

待验证假设：

  • 结果优先能减少常规任务监督时间，且不增加未覆盖范围的错误接受。
  • 共享口径比增加解释性文案更能减少人与 Agent 的核对。
  • 精度难例也存在可视化价值，价值取决于关系复杂度而非“精度”标签。
  • 结构化失败交接比完整聊天历史更有助于接管。
  • 自定制 Toolkit 的长期成本集中在语义、兼容和维护，而不仅是首次生成。

本研究没有为上述假设设定已证明的提升百分比；试点获得基线后再约定目标。
