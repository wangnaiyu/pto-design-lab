PyPTO Fusion Performance Diagnosis PRD

本 PRD 面向 PyPTO Toolkit 的融合算子性能诊断能力，把匿名研究归纳与 issue #2141 共同暴露的“看见慢 task 但无法归因”问题， 转化为从采集、归因、下钻、源码动作到复跑验证的完整产品闭环；能力按 P0–P2 分期交付。当前 canonical Demo 已覆盖核心诊断主线与 预计复跑，真实 P2 paired-run 对比仍是产品目标，不作为当前已采集能力宣称。

1. 产品判断

Fusion Performance Diagnosis 的第一期不应被定义为 Memory Viewer，也不应被做成大而全 Trace Viewer。 它的核心价值是把一个慢 task 自动解释成可行动的根因假设、证据强度和下一步 PyPTO 修改动作。

核心用户问题 看得到 task 慢，但不知道是计算、等待、依赖、UB pressure、spill-like 行为还是额外 GM/UB 搬运导致。
产品机会 把 PyPTO Toolkit 从执行可视化工具推进为融合算子性能诊断入口。
设计原则 先归因，再下钻；痛点绑定动作；建议必须能被下一轮运行验证。

2. 背景与问题

当前用户通过 debug_options={"runtime_debug_mode": 1} 采集运行上下文，同一轮得到程序结果与 merged_swimlane.json。这套机制可以让用户看到执行时间线，却没有把异常时间、内存压力、等待关系、 PMU counter、program.json、计算图和源码动作串成诊断链路。

设计研究显示，用户情绪谷底并不发生在采集或打开泳道图时，而是发生在“已经看到慢 task，却只能靠经验猜根因”的阶段。 竞品分析进一步说明，成熟性能工具的优势不是图表数量，而是选择窗口、时间线、资源指标、事件详情和行动出口之间的联动。

现状痛点 用户真实意图 产品化转译
打开泳道图后需要手工找慢 task、读依赖、看 copy 节点。 先知道哪几个 task 最值得看，以及主导瓶颈是什么。 提供 Top abnormal tasks / wraps 与 bottleneck type。
task bar 只有总耗时，用户无法区分干活、搬运和等待。 知道时间花在 compute、memory move、wait 还是未解释区间。 提供 compute / memory move / wait / unaccounted 分段泳道。
怀疑 UB pressure 或 spill-like 行为，但没有证据。 确认 peak live memory、UB headroom、额外搬运和贡献对象。 提供 Memory Pressure 下钻与 Top contributors。
试错调 tile、nbuffer 或融合边界后，很难证明因果。 用下一轮运行证明动作是否有效。 提供 Before / After 诊断对比和调优记录沉淀。

两个来源场景的收敛

本课题证据来自两类不同的工作场景：一是算子开发者的通用算子 profiling 调优（匿名研究归纳，一手证据，工具链为 Profiling Summary → MindStudio Insight → 自研表格 → 代码）， 二是 issue #2141 的 PyPTO 融合算子诊断（merged_swimlane.json）。两者入口不同，痛点结构同构。本 PRD 不做两套割裂界面， 而是把两个场景收敛到同一条「采集 → 归因 → 下钻 → 动作与验证」主线：通用 profiling 场景贡献「自动算 + 直接找」能力，融合诊断场景贡献「归因下钻 + 复跑验证」能力，合起来对应「自动算、直接找、全预判」。

诊断主线阶段 通用 profiling 场景（匿名研究归纳） 融合诊断场景（issue #2141） 收敛后的产品能力
采集 Capture 打印 Profiling summary，凭经验判 Compute / Vector / MTE2 bound。 runtime_debug_mode 同轮产出 merged_swimlane.json。 保留采集入口，自动绑定本轮产物并预判 bound 方向。
归因 Attribute 自研表格手输矩阵尺寸算理论性能。 泳道图人工找慢 task，无法归因 UB / 搬运。 Top 异常 task + 瓶颈类型 + 理论 vs 实测 gap（FR-02、FR-09）。
下钻 Drill Vector 指令耗时无基线；图码需人工对应。 需下钻 peak live memory、UB headroom、Top contributors。 分段泳道 + 内存压力面板 + 指令耗时基线 + 源码联动（FR-03/04/07/10）。
动作与验证 Act & Verify 多版方案逐一试，局部调优引发全局劣化。 反复改 tile / nbuffer，因果不确定。 建议自带验证指标 + Before/After 复跑对比（FR-08）。

3. 目标用户

目标用户：Fusion Performance Engineer

PyPTO / CANN 高阶算子开发与性能调优用户，主要处理大模型 RoPE / Attention 相关融合算子性能交付。 该用户能够阅读泳道图和计算图，也能修改 tile、融合策略或 vec_nbuffer_setting。

他的核心困境不是“不会调”，而是工具没有把性能现象翻译成足够可信、可执行、可验证的根因证据。

同一角色在实际工作中跨两个业务任务：LLM RoPE / Attention 融合算子交付，以及通用算子 profiling 调优；本 PRD 的诊断能力需要同时服务这两类调优。

非目标用户

  • PyPTO 入门用户：优先需要教程、示例代码和基础错误排查。
  • 纯算法研究者：主要关心算法效果，不负责融合算子性能归因。
  • 应用层调用方：只需要端到端趋势或整体 profiling 报告。
  • 平台管理视角：关注资源利用和调度概览，不修改 tile / nbuffer / fusion boundary。

4. 目标与非目标

产品目标

  • 让用户在打开运行产物后 1 分钟内看到 Top abnormal tasks 与主导瓶颈类型。
  • 把慢 task 的时间拆成 compute、memory move、wait、unaccounted 四类解释。
  • 对内存相关异常给出 peak live memory、UB headroom、extra movement 与 Top contributors。
  • 把诊断结论绑定到 task、wrap、tensor、op、program.json、计算图和源码位置。
  • 让每条建议都能被下一轮运行的 task time、extra movement、UB pressure 或 utilization delta 验证。

非目标

  • 不在第一期做通用 Trace Viewer 或可任意配置 counter 的专家自由探索工具。
  • 不把 PMU CSV 表格直接暴露为产品主能力。
  • 不把 Memory Viewer 作为独立终点，内存信息必须回到诊断和动作。
  • 生产环境第一阶段不自动改写用户代码（仅证据 + 建议 + 跳转出口）；canonical Demo 的“一键应用”只刷新 构造 建议代码预览与“预计复跑”，不会改写真实源码，也不会生成已采集 After。
  • 不覆盖所有算子类型，先聚焦融合 task、wrap 与 RoPE / Attention 类高频性能问题。

7. 功能需求

FR-01

运行产物自动绑定

系统应识别同一轮运行中的 merged_swimlane.json、program.json、计算图、PMU 文件与源码映射状态，并提示缺失项。

  • 必须展示当前 run id 或可读的运行时间标识。
  • 必须标记数据完整性：complete、partial、missing。
  • 缺失关键证据时，不得给出高置信诊断。
FR-02

Top abnormal tasks / wraps

系统应按 duration、severity、bottleneck type 和 evidence level 展示优先排查对象。

  • bottleneck type 初期至少包括 compute、memory movement、wait、UB pressure、unaccounted。
  • 点击列表项后，泳道图和详情面板必须同步定位到对应 task / wrap。
  • 每条异常必须展示“为什么它异常”的一句话解释。
FR-03

分段泳道图

异常 task bar 应分解为 compute、memory move、wait、unaccounted 四段，并展示各段 absolute time 与 ratio。

  • dominant segment 应可被视觉或排序识别。
  • 点击 segment 后右侧详情只解释当前 segment。
  • unaccounted 不能被隐藏，必须提示证据不足或计量缺口。
FR-04

Memory Pressure 下钻

系统应针对内存相关异常展示 live memory 曲线、UB headroom、extra GM/UB movement、copy edge 与 Top contributors。

  • Top contributors 至少按 tensor、op、fusion fragment 或 task 归因。
  • 每个 contributor 必须能追溯到数据来源字段或关联对象。
  • 建议动作应明确指向 tile、nbuffer、fusion boundary 或中间结果减少。
FR-05

Wait Chain 下钻

系统应区分 predecessor wait、schedule wait、sync wait、resource / uncovered gap，并高亮信号方、等待方和 peer task。

  • 等待关系应支持从当前 task 跳到 critical peer。
  • 当等待证据不足时，应提示无法区分等待类型。
  • 等待诊断应避免与 memory movement 诊断互相覆盖。
FR-06

Pipeline Balance 诊断

系统应把 PMU group 转译为 AIC / AIV / MTE / FixPipe / Scalar 等维度的 utilization、dominant counter 和 critical lane。

  • 不得把 PMU CSV 直接作为主体验。
  • 必须解释 MTE-heavy、AIV idle、UB conflict、构造 reuse failure 等诊断标签的证据。
  • 当 counter 覆盖不足时，应降级为“趋势提示”而非强诊断。
FR-07

分层回跳与源码联动

诊断结论应能沿编译/执行分层链路回跳到源码，保留 rootHash、callOpMagic、leafHash 等上游 literal 作为跨层 join key。

  • 分层链路：执行逻辑图 → Execute Graph（按 func_id + ring/scope 对齐）→ Block Graph（Execute call node 即 block 调用）→ Tile / Tensor Graph（编译溯源）→ 源码；泳道 task bar 可按 task identity 直达 Block Graph。
  • 定位到“哪一个”图靠溯源键三元组唯一钉住：leafHash→block、callOpMagic→call、rootHash→tensor op，不靠推测；需编译各 pass 落 parent↔child 溯源映射以解决一对多扇出。
  • 缺 name_map 或溯源映射时，节点退化为匿名 task(rXtY)，跳转降级为展示可复制身份 + 跳到最近可用层。
  • 执行逻辑图定义与 schema 见 关联研究材料；其 Execute Graph 若为聚合参考预览，精确前向跳转需原生 execute graph 产物（待编译侧确认）。
  • 跳转失败时，应展示可复制的对象标识；源码动作建议必须说明它影响哪个诊断指标；不改写上游字段名、trace key 或文件名。
FR-08

已采集 Before / After 诊断对比

系统应支持两轮运行的 task identity matching，并比较 task time、extra movement、wait ratio、UB headroom 和 pipeline balance。

  • 匹配状态使用 matched / partial / unmatched / unavailable 与候选对象表达；不使用缺少校准依据的启发式 confidence 数值。
  • 只有 operator、scenario / workload、配置、metric definition 与显式 comparison identity 一致时，才可标记 matched 并显示 collected delta。
  • 对比结果应区分“改善”“恶化”“无显著变化”“证据不足”。
  • 对比结论可沉淀为团队调优记录或后续 agent 输入。
FR-09

理论性能推演对照

系统应基于 tensor 形状、搬运量与带宽自动推演理论耗时与带宽利用率，作为实测 task bar 的基准线，替代研究归纳中「每个算子手搓一张表」的人工计算。

  • 不要求用户手工输入矩阵 A / B 尺寸，尽量从产物自动取形状。
  • 必须同时展示理论值、实测值与两者 gap，gap 是待解释差额，不等于可实现的优化收益提示。
  • 必须标注推演口径与假设（带宽基准、精度、是否含 overlap），口径不足时降级为「参考区间」。
FR-10

指令耗时基线库

系统应沉淀标准化指令 / API 耗时基线（尤其 Vector 类），把研究归纳中「一条 vector 单元应该耗时多少没有资料」的经验盲区变为可查参考。

  • 基线至少覆盖常用 compute / vector / MTE 指令，并可随硬件、精度分档。
  • 分段泳道与 Pipeline Balance 诊断应能引用基线解释「这段是否偏慢」。
  • 缺基线数据时降级为趋势提示，不给高置信指令级诊断。
FR-11

时间轴状态缩略图（执行逻辑图 / A5内存）

系统应在时间轴提供状态截图序列：左侧下拉默认「计算图」（执行逻辑图），另有「A5内存」；右侧为所选视图在各时间点的状态缩略图，随时间推进高亮 active 对象。

  • 「计算图」随时间高亮 active 计算图节点；「A5内存」高亮 active 硬件对象。
  • 点击缩略图进入该视图完整页面 / 新 IDE tab；执行逻辑图见 关联研究材料，A5内存与硬件视图调用设计系统真实资源并对齐 ascend-a5-950-hardware。
  • 缺执行逻辑图时间片映射时，降级为 task / wrap 热点缩略图。

交互与视觉设计手法

面向高阶调优专家，交互与视觉手法都服务于一个目标：压缩「看见慢 → 知道为什么 → 该改哪里」的注意力成本，并让每一步都可信、可验证。 以下手法约束 P0–P2 的默认视图与下钻表达，避免退化成堆叠 tracks 的通用 Trace Viewer。

设计手法 类型 解决的痛点 表达 / 交互方式
归因漏斗 · 渐进式披露 交互 默认视图信息过载、专家在满屏 track 里扫。 默认只暴露 Top 1–3 异常与瓶颈类型，证据随下钻逐层展开。
四视图联动 · Brushing & Linking 交互 图与代码无映射，人工对应。 泳道图 / 内存曲线 / 计算图 / 源码共享选择态，点一处全高亮同步。
证据强度即视觉编码 视觉 推断被包装成事实，误诊伤信任。 用饱和度、虚线、hatch 纹理编码 high / partial / insufficient，不足时降级为「可能原因」。
理论基准线 · Reference Line 视觉 理论性能靠手工表格算。 推演理论耗时作为基准叠加在实测 bar 上，gap 是待解释差额，不等于可实现的优化收益。
语义缩放 · Semantic Zoom 交互 不同粒度间切换心智成本高。 同一 task 从总耗时 → 分段 → 单 tensor 贡献逐级放大。
就地差分 · Diegetic Diff Overlay 交互 / 视觉 调优靠试、因果不确定。 复跑 delta 直接叠加在原泳道与指标上，把验证嵌回看问题的地方。

竞品洞察与观测体验设计要求

基于竞品分析（Nsight Systems / Nsight Compute / Chrome DevTools / Perfetto / PyTorch Profiler），把“额外搬运 / 等待 / 流水利用率”三类观测体验与 Chrome 式时间轴的可迁移范式，沉淀为 P0–P2 视图的设计要求。 详见 关联研究材料。

观测对象 竞品范式 设计要求 关联需求

核心判断：竞品的优势不是图表数量，而是“选择窗口 → 全局总览 → 多轨展开 → 详情同步”的联动。PyPTO 的差异化是把这套观测进一步绑定到 tensor / op / leaf task / wrap / 源码 / 调参动作。 默认视图必须“少而强”，不退化为大而全 Trace Viewer 或 PMU CSV 表；内存信息必须回到诊断与动作，而不是停在 Memory Viewer。

时间轴区域设计规格

把上述范式落成 PyPTO 时间轴区域的三层结构（示意见 竞品分析蓝图）：一个选择窗口驱动三层同步过滤。

层 内容 交互规格
① 顶层概览 ≤5 条全局曲线：Host CPU、Device CPU / AICPU、AICore active、UB headroom / live UB、Memory bandwidth / MTE busy。通用算子开发默认先看 AICore active；本融合诊断场景优先解释 UB headroom / live UB 和 MTE busy。 拖拽选择时间窗口，驱动全视图同步过滤；曲线数量首期上限 5，避免退化为 PMU 表；hover / 详情侧栏解释单位、阈值和当前选区含义。
② 状态截图序列 左侧下拉：默认「计算图」（执行逻辑图），另有「A5内存」；右侧为所选视图在各时间点的状态缩略图。 「计算图」随时间前进高亮当前 active 计算图节点；「A5内存」高亮当前 active 硬件对象。点击缩略图进入该视图完整页面或新 IDE tab。执行逻辑图定义与 schema 见 关联研究材料。
③ 多进程融合泳道 AICPU runtime、AICore（AIC0 / AIV0 / AIV1）、Memory（GM↔UB、UB live 带容量线）、Sync / deps。 按 wrap 聚合可展开 1C2V；选中等待段高亮 critical peer；Memory 作为独立 process-like 轨道与 AICore 对齐。

数据与资源前提：② 的「计算图」缩略图依赖运行产物稳定绑定 program.json、rootHash、callOpMagic、leafHash；缺时间片映射时先用 task / wrap 热点缩略图替代。「A5内存」缩略图与完整视图必须调用设计系统真实资源（memory-architecture-layout、memory-reuse-viewer、hardware-architecture-viewport、aic-core-object / aiv-core-object），对齐 ascend-a5-950-hardware。

Demo 故事脚本

本 demo 用一个连续故事呈现「性能调优」场景，并把当前可观察能力与未来产品目标分层：canonical Demo 负责 Run / Task 诊断、构造 建议应用与预计复跑；真实 collected Before / After 只有在取得有效 paired run 后才进入 FR-08。

主线与 UX 分析的端到端融合场景一致：主角是融合性能工程师，目标是把一个性能不达标的 A5 融合算子 attention_fusion_case 调到可交付。 他不再靠 summary 经验判 bound、手搓表格算理论值、肉眼对图找码、盲目试错，而是被 Toolkit 一路带到「知道为什么、该改哪里、改了有没有用」。 故事沿「采集 → 归因 → 下钻 → 自动优化 → 验证」推进，共十幕；其中自动优化在 demo 中模拟“一键改写算子代码”以闭合调优环。

Demo 设定：算子为 A5 融合算子（attention_fusion_case），因此查看内存、硬件架构、算子代码等场景均采用 A5 设计资源。凡涉及硬件架构、内存架构、AIC/AIV 内部对象、内存复用等可视化，必须调用设计系统的真实 pattern（hardware-architecture-viewport、memory-architecture-layout、memory-reuse-viewer、aic-core-object / aiv-core-object）并对齐 ascend-a5-950-hardware 资源，不另造视觉。

幕 用户动作与交互 触发能力（FR / 分期） 界面呈现与关键数据（占位） 呼应原则 / 设计手法
1. 采集与绑定 用 runtime_debug_mode 跑一轮 attention_fusion_case，打开 Toolkit。 FR-01 运行产物自动绑定 自动识别 run#12 · 2026-08-18 09:40，绑定 merged_swimlane.json、program.json、PMU、计算图、source map；完整性标记 complete。 保留既有机制；减少手工找文件与错配上下文。
2. 总览与归因 进入诊断总览看 Top abnormal 排名；拖动时间轴，状态缩略图序列（默认执行逻辑图）随时间高亮 active 节点，先建立运行时对象状态感知。 FR-02 Diagnosis Overview · 时间轴缩略图 Top：DEV0-C05-T029 · bottleneck = memory movement · evidence = high；次级 T019 compute(mid)、T037 wait(low)；缩略图 active 节点随 t1→t5 推进。 先归因、再下钻；归因漏斗 · 渐进式披露。
3. 理论对照 在慢 task 上叠加理论耗时基准线，看 gap。 FR-09 理论性能推演对照 理论 128.0 us / 实测 156.0 us / gap +28.0 us / 带宽利用率 62%。 理论基准线 · Reference Line（替掉手搓表格）。
4. 分段泳道 点 task bar 展开分段，逐级放大。 FR-03 Segmented Swimlane compute 26.9% / memory move 39.3% / wait 25.6% / unaccounted 8.2%；dominant = memory move。 语义缩放 · Semantic Zoom；unaccounted 不隐藏。
5. 内存压力 点 memory 段下钻内存压力与 Top contributors；把时间轴缩略图切到「A5内存」，点击 active 硬件对象缩略图，在新 IDE tab 打开 A5 内存可视化完整视图（调用真实设计资源）。 FR-04 Memory Pressure · FR-10 指令耗时基线 peak live 232.0 KiB、UB headroom 24.0 KiB、extra GM/UB movement 384 KiB、Top contributor k_cache_tile（GM→UB reload）；Vector 指令段对基线偏慢 1.7×。 痛点绑定动作；把 UB/spill 从经验判断变成证据。
6. 等待链 点 wait 段，区分等待类型并跳到 critical peer。 FR-05 Wait Chain wait 拆分：sync wait 18.9 us（critical peer AIC-T009）、schedule wait 4.1 us、uncovered gap 2.6 us。 证据强度视觉编码（区分等待类型，不与搬运互相覆盖）。
7. 流水均衡 打开 Pipeline Balance，看 PMU group 转译镜头。 FR-06 Pipeline Balance MTE2 util 81%（MTE-heavy）、AIV idle 34%、UB conflict flag；PMU 覆盖 partial → 标注「趋势提示」而非强诊断。 证据强度视觉编码（覆盖不足降级为趋势）。
8. 分层回跳 点时间轴「计算图」缩略图，新 IDE tab 打开执行逻辑图；沿链路回跳：执行逻辑图 → Execute Graph → Block/Tile/Tensor Graph → 源码（泳道 task 则按 identity 直达 Block Graph）。 FR-07 分层回跳与源码联动 用 (leafHash, callOpMagic, rootHash) 逐层钉住节点：leafHash→block、callOpMagic→call、rootHash→tensor op；program.json 片段 + 源码 attention_case.py:96 同步高亮。 四视图联动 · Brushing & Linking（消除图码无映射）。
9. 一键自动优化 点“应用建议”，系统模拟自动改写算子代码（tile / nbuffer）。 Demo 模拟 · 自动优化闭环 自动改写：tile_k 256→128、vec_nbuffer_setting 2→1、收紧融合边界；代码 diff 就地高亮，每条改动声明预期验证指标（task time↓ / movement↓ / headroom↑）。 建议必须可验证；痛点绑定动作；演示完整闭环。
10. 预计变化与已采集验证 应用建议后先查看同口径 构造 projection；取得有效 paired run 后再进入 collected 对比。 Demo projection + FR-08 当前 Demo：task 12.8μs → 预计复跑12.3μs；已采集 run 对比 unavailable。未来满足 matched contract 后才显示 collected delta 并沉淀团队记录。 预计与已采集分层；不把预测包装成验证。

脚本中的 run id、task id、指标数值、源码位置、contributor 名等均为叙事占位，只用于表达交互流程与信息结构，不构成上游事实断言。 结构化 demo 数据已由 Codex 接手生成至 fusion-diagnosis-a5-demo-data.json v0.3.4，数据等级为 构造 / schema-generated / 公开准入；当前版本已按本地 testdata / 样例数据统计校准信息量与数据量，按 A5 / Ascend 950 package 拓扑修正为 32 AIC + 64 AIV，补齐 project / run / 泳道显示 ID / runtime taskId / 架构定位 ID，并新增执行逻辑图、图层映射、源码映射、导航场景、代码片段和性能概览指标；若进入实现或对外性能叙事，仍需按 PyPTO 本地镜像 / 官方文档 / 样例数据替换为已核实材料。

8. 数据需求与诊断契约

本 PRD 不新增上游事实断言，只把现有研究中的字段和产物诉求整理为产品数据契约。真实字段、路径和 schema 需要在进入实现前回到 PyPTO 本地镜像、官方文档或样例数据中校验。

数据域 用途 关键对象或字段 缺失时的降级
Execution timeline 定位 task / wrap、计算 duration 与异常排序。 merged_swimlane.json、exec_start/end、task identity、wrap mapping。 只展示时间线与人工选择，不给出自动严重度。
Program linkage 把诊断回连到 PyPTO 表达和计算图。 program.json、rootHash、callOpMagic、leafHash、operand hints。 保留对象标识，但不显示源码 / program 跳转。
Memory movement 判断额外 GM/UB 搬运、copy edge 与 Top contributors。 copy in/out、GM/UB bytes、raw tensor memory range、movement summary。 只展示 task 分段中的 memory move ratio，不给 contributor 归因。
Live memory 计算 peak live memory、UB headroom 与 pressure trend。 live tensor set、peak bytes、UB capacity reference、tensor lifetime。 不判断 UB pressure，只提示需要补充 live memory 数据。
Wait / sync 区分 predecessor wait、schedule wait、sync wait 与 peer relation。 syncEvents、ready time、schedule wait、peer task mapping。 等待只作为未解释或弱证据段展示。
PMU counters 解释 pipeline balance、MTE-heavy、UB-conflict 等标签。 PMU group 2/4/6/7/8 counters、core mapping、total cycle。 仅显示趋势，不给高置信 pipeline 诊断。
Run comparison 验证调优动作是否有效。 run id、task identity matching、metric delta、diagnosis delta。 允许人工选择两轮任务后做局部对比。
Graph layers & provenance 支持 FR-07 分层回跳与“定位到哪一个图”。 execute graph、name_map、parent↔child 溯源映射（rootHash↔tile↔leafHash）、func_id / ring / scope。 缺映射时退化为匿名 task(rXtY)，只展示可复制身份 + 最近可用层。
Theoretical model 推演理论耗时与带宽利用率（FR-09）。 tensor shape、搬运量、带宽基准、精度、是否含 overlap。 口径不足时降级为“参考区间”。
Instruction baseline 解释指令级是否偏慢（FR-10）。 标准化指令 / API 耗时基线（按硬件、精度分档）。 缺基线时降级为趋势提示。
Runtime graph & memory state 时间轴状态缩略图与完整视图（FR-11）。 runtime task DAG timing、执行逻辑图时间片 active 映射、A5 硬件对象状态、设计系统真实资源。 缺时间片映射时退化为 task / wrap 热点缩略图。

诊断输出必须显式区分 evidence level。缺少 memory、wait 或 PMU 证据时，系统应降级表达为“可能原因”或“证据不足”， 避免把推断包装成事实。

9. 成功指标与验收标准

指标 衡量方式 期望方向
首次定位时间 从打开运行产物到识别 Top abnormal task 与主导瓶颈的时间。 显著短于人工读泳道图。
诊断覆盖率 异常 task 中可给出 bottleneck type 和 evidence level 的比例。 P0 覆盖 memory movement / UB pressure 相关问题。
建议可执行率 诊断建议能绑定 tile、nbuffer、fusion boundary、tensor/op/source 的比例。 减少“泛泛建议”。
验证闭环率 完成修改后能通过下一轮运行看到 delta 的问题比例。 P2 后成为默认闭环。
证据可信度 用户是否认可诊断证据足以支撑下一步修改。 高于纯 timeline / CSV 观察。

PRD 验收标准

  • P0 完成时，用户可以从异常列表进入分段泳道和 Memory Pressure 面板，完成一次“慢 task -> 内存证据 -> 调参方向”的诊断。
  • P1 完成时，用户可以区分 memory movement、wait chain 与 pipeline imbalance，减少误把等待当搬运或误把搬运当计算瓶颈。
  • P2 完成时，用户可以把诊断跳回源码 / 计算图 / program.json，并通过两轮运行对比验证动作效果。

10. 风险与开放问题

风险：证据链不完整导致误诊

如果 memory、wait、PMU 或 source map 缺失，强行给出单一根因会伤害信任。需要把 evidence level 作为一等输出。

风险：默认视图变成复杂 Trace Viewer

竞品启发应服务于诊断闭环，而不是堆叠 tracks 和 counters。P0 默认视图必须少而强。

开放问题：UB capacity 与 headroom 如何标准化

需要确认不同硬件、task 类型和采集粒度下，UB headroom 的计算口径与阈值。

开放问题：task identity matching 的稳定键

Before / After 对比依赖跨轮匹配，需要确认使用 task id、wrap、hash、op path 还是组合键。

开放问题：建议模板的边界

第一期建议应偏“方向 + 证据 + 验证指标”，还是可以给出更具体的 tile / nbuffer 参数候选，需要结合真实样例验证。

开放问题：source map 缺失时的行动出口

如果源码位置不可用，是否以 program.json、计算图节点、tensor/op 名称作为临时出口，需要产品和实现共同确认。

开放问题：分层溯源映射是否可得

FR-07 的“定位到哪一个 block / tile / tensor”依赖编译各 pass 落 parent↔child 溯源映射与原生 execute graph；FR-11「计算图」缩略图依赖执行逻辑图时间片映射。需与编译侧确认这些映射的可得性与稳定键。
