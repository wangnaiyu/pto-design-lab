01

把 Agent 放进算子开发的判断与实验中

报告主张：人与 Agent 围绕同一个工程任务、同一组证据，持续完成分析、行动和验证。

算子开发中的核心困难，是把数学语义、编译变换和硬件运行联系起来。Agent 可以承担检索、整理、比较和候选生成；用户需要理解依据，决定实验是否值得做，并判断结果能否支持下一步。

本报告中的 Agent in the loop，指 Agent 持续参与用户主导的专业任务：带着可追溯上下文取证，把建议变成受控实验，再让结果返回同一任务。

这是本方案的工作定义。它与“人在自动化流程中审批”可以同时存在；设计重点是双方何时接手、共享什么，以及凭什么继续。

设计部需要判断的三件事

  1. 是否抓住专业判断中的断点，而不仅是增加对话入口。
  2. 自动化边界是否让用户既能推进任务，也能及时纠正。
  3. 机制是否能从性能诊断扩展到编译、精度与开发任务。

本次报告的论证顺序

先还原算子开发的任务和证据，再说明协作分工；由分工推导契约与系统设计，最后用完整场景检查机制是否闭合，并给出验证路径。

建议阅读：领导概览看 01–04、10；机制与工程讨论看 05–09；证据核对看 11。

研究 / 文档依据原型交互走查目标设计 / 本次展开用户收益待验证

下文保留 PPT 的研究、四个设计方向、协作流程、体验架构、异常恢复和落地验证内容，并补充数据契约、执行边界、状态模型与多任务场景。[1][2][3]

02

算子开发的对象，一直在变化

要让 Agent 帮助判断，首先要知道当前讨论的是公式、图中的节点，还是某次运行的动态实例。

在本次核验的 PyPTO 2.x Tensor 路线文档中，Tensor Graph 表达计算逻辑，Tile Graph 引入分块和存储位置，Block Graph 承接子图划分与硬件相关优化，Execute Graph 描述执行依赖。运行时再产生任务实例与时序证据。跨层关联是一项需要校验的能力；同名节点、同一子图或同一文件路径，都不能单独证明它们就是当前要修改的对象。[8]

工作阶段用户真正需要判断Agent 可以组织的证据本轮应留下什么
设计边界数学语义、输入范围、精度约束和硬件目标是否清楚参考实现、API 适用版本、shape / dtype、算子边界可评审的规格与验收样例
开发与编译实现是否成立，失败发生在什么阶段源码快照、编译日志、Pass 前后图或 IR、版本最小复现、候选修改和构建结果
精度调试判定标准合理吗，差异从哪里开始golden 数据、阈值、输入、Tensor / Pass 检查结果首个可定位差异与回归用例
性能调优什么限制性能，修改有没有净收益泳道、同步、计数器、依赖、基线与候选 run带适用范围的实验结论
集成与复用局部收益能否保留到真实负载输入集合、环境、正确性回归、算子 / 模型级测量可重跑记录与适用边界

三个领域特性，决定交互不能止于文本建议

静态定义 ≠ 动态实例

同一段计算可能在多个轮次、不同调用中执行。用户需要知道结论针对哪一次，而不仅是节点叫什么。

局部改善 ≠ 整体改善

缩短一个等待区间，仍可能把瓶颈移到另一个任务。比较必须说明覆盖的是局部区间、算子还是模型。

可运行 ≠ 可接受

编译成功之后仍需检查精度；性能更快之后仍需检查输入覆盖和回归。验收标准必须先于实验结果。

领域流程依据本地官方文档快照；交互含义为设计推导。本文不将这条 Tensor 路线泛化为 PyPTO Pro / 3.0 的统一实现架构。[8][9][10]

Issue #1567 的研究摘要提到：用户用 Agent 分析 JSON，经过多轮指标对齐，结果才与泳道图接近。开发者研究则指出图到源码的断层、局部优化副作用和验证困难。它们共同支持一个设计推断：更好的回答，依赖更清楚的证据对象与判断条件。[4][5][1]

用户判断障碍正式设计方向作用机制需要验证的收益
不知道证据能回答到什么程度证据准入先于诊断先检查覆盖、口径与缺失项，再限定结论强度能选择继续分析或补证据
结论落不回同一对象跨工作面保持同一对象保留对象引用、关联来源与返回位置减少重新找对象和误认实例
不知道建议是否值得试输出帮助用户做出行动判断同时呈现首要假设、反例、调整项、风险与验证条件更有依据地选择实验
改前改后无法可靠比较以可比复跑结束一次建议限定变更、隔离实验、核对可比条件再解释结果减少把不相关差异读成收益
上述四个方向沿用正式体验策略“共享可被追问的性能证据”。后面的系统模块是它们的实现展开，不另起一套策略分类。[1]

把人的介入放在判断变化处

用户不需要确认每一次读取；当目标、对象、行动范围或结论发生变化时，介入才有意义。

依据本次提供的机制流程重新绘制。蓝色为 Agent 分析，绿色为用户动作，菱形为判断点；侧边保留补证据、拒绝或调整、不可比路径。虚线仅表示回流，不表示可跳过准入与执行检查。

查看同一流程中的角色分工

专业协作的最小单位是一轮实验：目标明确、证据可检查、行动可约束、结果可解释。Agent 可以在既定任务范围内连续取证和比较，用户在关键判断处补充信息、纠正假设、批准实验或结束任务。图中是目标流程，当前 Demo 的执行与复跑仍为模拟。[1][2][3]

一份会话，三个不同对象

工程 / Workspace

决定读写范围和可执行环境。仅有运行产物时，可以分析，但不能据此宣称具备源码修改能力。

运行 / Run

保存一次执行或采集的证据。一个任务可以引用多个 run；选择 run 不必自动创建新会话。

任务 / Task

承载目标、判断、审批、实验与结果。切换画布或再次追问，应继续同一任务。

以上三轴语义与分工来自现有架构设计；默认自动化粒度、资源预算和集成介入属于本次方案展开，仍需目标用户与工程联合验证。[2]

05

四个方向，需要可执行的契约

机制要同时约束界面呈现、Agent 行为和工具调用，才能在多轮任务中持续成立。

机制一 · D1 / DP1–DP2证据准入先于诊断

准入不是给整份文件一个“健康分”。它必须回答：针对当前问题，这些证据允许得出多强的结论？例如，时间条可以支持“这里存在空隙”的观察；要解释空隙来自同步、调度还是采集缺失，还需要相应通道与关联证据。

检查项需要保存的内容对交互的影响
覆盖范围对象、设备角色、轮次、采样区间、截断信息覆盖不足时说明缺哪一段，而非宣称没有问题
指标含义单位、计时基础、统计方式、计数器配置摘要和详情使用同一指标定义
产物可用性原始文件、解析结果、错误、缺失通道缺失不得渲染成 0 或正常
允许行为可分析但有限制 / 仅解释缺口在结论出现之前决定是否进入诊断

本次性能主场景为“可用但有限制”；证据不足场景缺少同步、等待与 Group 2 计数，原型会停在准入说明。准入结论随证据变化重新计算，不能在任务开始时检查一次后永久沿用。后一句为生产化建议。[3][6]

机制二 · D2 / DP3–DP5跨工作面保持同一对象

回答、泳道、计算图和源码候选共享逻辑对象引用 objectRef，但每一跳都保留自己的关联证据。运行实例被精确识别，不等于它已精确映射到当前源码。用户点击结论时，应能看见对应现场；证据不够时，应能看见候选或缺口。

关联状态用户看到什么允许的动作
exact · 精确关联当前这一跳由明确标识支持直接定位该证据对象；源码仍单独校验
derived · 推导关联推导方法及依据带标记检查候选，不将推导冒充原始事实
ambiguous · 关联不唯一多个候选及可区分信息先确认，阻止基于唯一源码对象的审批
unavailable · 不可用缺失关联与补足条件保留现有证据浏览，不制造跳转链接

上下文既包含“现在选中了谁”，也包含“这次问题绑定的是谁”。浏览另一个对象不应悄悄改写正在审批的实验；切换正式任务对象时，应确认新范围并重新检查受影响证据。[1][2][3]

Context Frame：公共语义与产品线 adapter

现有设计包含 productLine、schemaVersion、handle、focus、objectRef、runtimeInstance、sourceAnchor、joinMethod、confidenceClass、candidates、evidenceHealth、runComparisonIdentity、staleness、rawIds。

公共字段描述语义；adapter 保存各产品线原始 literal。不同层的 task、function 与源码不能靠同名字段直接相连。本文不定义新的 PyPTO 3.0 字段转换，也不把这份 Context 设计说成上游已有公共 API。

机制三 · D3 / DP6–DP7输出帮助用户做出行动判断

一条建议应当足以让用户选择实验。核心不是展示更多分析文本，而是把观察、假设、行动和验证分开，让用户知道什么已经看到、什么仍在猜测。

结构示例 · 非运行结论

先验证“同步释放时机是否延长局部等待”

观察
指定运行实例的等待区间与释放事件存在时间关系；关联范围仅限当前选区。
假设
释放时机可能限制其中一个等待方；还需排除必要依赖及其他执行约束。
调整
只改变一项可解释参数，并展示最小修改范围。真实修改点需要源码和构建关联。
风险
提前释放若破坏依赖，可能造成精度或功能错误；等待也可能转移到其他路径。
验证
正确性先通过，再比较相同口径的局部指标，并检查更大范围是否回归。

经验性启发应标明适用条件，不能因为 Agent 熟悉“常见瓶颈”就把它当成本次现场根因。若证据不足以区分竞争解释，下一步可以是一次补采实验，而不是立即改代码。[1][3]

机制四 · D4 / DP8–DP10以可比复跑结束一次建议

候选修改先进入隔离实验，再按预先声明的条件检查结果。“任务执行成功”“结果允许比较”“假设得到支持”是三个不同判断。其中任何一项失败，都不应被最后一句“完成”覆盖。

验证层通过条件不能替代的下一层
执行完成构建 / 测试 / 采集阶段给出可确认结果退出码成功不能证明指标有效
数据有效预期产物已落盘，覆盖与口径可用有两份文件不能证明可比
条件可比输入、环境、统计与允许差异满足比较契约条件一致不能证明差异稳定
判断成立指标变化支持假设，正确性和回归检查满足标准局部有效不能证明算子 / 模型整体获益
真实改码时，源码版本当然会变化：需要“允许的差异”，而不是要求所有字段完全相同

D3 的 构造 paired fixture 保持比较身份不变，只执行确定性参数变换。真实工程中，候选代码和构建标识会变化，必须记录 baseline → candidate 的已批准变更，并检查其余条件是否受控。意外版本漂移与计划中的改码，不能都归为“不一致”。这是对现有 comparison gate 的工程展开，尚未接入原型。

建议比较契约明确：输入 shape / dtype / batch、硬件与执行环境、软件版本、采集配置、指标定义、scope / timebase、轮次 / 统计方法、源码 / 构建来源，以及允许改变的参数或补丁。多轮测量需保留样本与离散程度；若噪声不足以支持判断，结论应是“尚不能确认”，而非强行判定成功或失败。

系统的核心，是任务状态与证据服务

下图为目标架构。已有方案提供概念分层，本节补充面向真实执行的职责与约束。

Agent 负责规划与解释，工具和服务负责执行可校验规则。只有在服务端同样检查证据、身份与授权，换一个 Agent 或恢复一个任务时，约束才不会只剩下一段提示词。图中的模块是职责划分，可以在首版合并进一个本地进程，不要求一开始拆成微服务。[2][3]

能力输入 / 输出设计关键约束

6.2 对话是呈现方式，结构化记录负责恢复任务

任务记录至少保存目标、上下文版本、活动对象、证据准入、候选方案、审批、执行 job、比较条件和结论范围。对话时间线从这些事件生成。画布开合只改变查看状态，不隐式批准提案，也不把执行中的任务改成已完成。[3]

独立状态维度示例状态为什么需要分开
任务阶段准入 → 分析 → 审批 → 复跑 → 验证描述当前推进到哪里
证据 / 关联可用但有限制；exact / ambiguous / unavailable控制允许得出的判断和定位
提案 / 执行待审批 / 已拒绝；排队 / 执行 / 失败 / 已取消区分人的决定和机器执行
比较 / 结论不可比 / 可比较；假设 / 得到支持 / 证据不足避免把执行完成自动写成结论成立
画布泳道 / 图 / 源码 / diff / 对照 / 关闭浏览行为不能改变实验状态

本次工程展开：建议把授权记录绑定到 proposalRevision、补丁摘要、上下文版本、目标工程、运行环境和动作范围。这些是候选字段，不是上游 schema。

  1. 准备时：展示改动、验证计划、预计成本与可撤销范围。
  2. 审批时：记录用户批准的是哪一版提案、允许写哪里、允许执行哪些阶段。
  3. 执行前：重新核对源码与构建、提案版本、授权范围。用户已改代码或 Agent 已改提案时，旧批准不能自动沿用。
  4. 执行后：记录真正发生的变更与产物；取消请求先显示“正在停止”，收到执行器确认后再标为已取消。
  5. 恢复时：基于 job 和事件记录核验状态。重复请求不得重复提交同一实验；中断后不靠聊天摘要猜测任务是否已完成。

6.4 Skill 版本、离线与数据范围

现有设计提出“受管本地能力 + 工程版本锁 + 可选团队覆盖”，并以网关解耦能力存放与 Agent 消费方式。版本锁有助于恢复当时的方法和配置，但不能保证生成模型再次输出完全相同内容。因此还要保存输入快照、实际工具结果和执行参数。[2]

数据边界体现在发送前

用户能检查哪些源码、日志和摘要即将进入当前 Agent；网关按任务范围裁剪数据。切换远端 Agent 或扩大资料范围时重新核对。只传 handle 不能自动消除泄露风险，后续展开仍需相同权限。

离线降级保留可用任务

可离线查看已有产物、运行已安装且环境满足的确定性检查。没有可用本地模型或执行器时，明确哪些分析与操作不可用；不要把“本地 bundle”描述成自动具备全部智能与硬件能力。

审计记录保存可观察的工具调用、输入输出引用、规则判断与用户决定，用于复现和排错；无需展示模型内部推理链。授权绑定、幂等、停止确认与恢复一致性尚属目标设计。

07

贯穿场景：一次同步等待诊断怎样走完整

以已走查的 GLM-4.5 / A5 构造原型为例，观察每一次介入解决了什么问题。

演示边界：当前 fixture 仅覆盖 glm-attn-a5-g2-20260702-074204:1:9000000000000030，显示对象为 1-46-141-79-46(QK-MatMul)。精确关联仅在这份原型产物内成立，源码映射不可用；“复跑”是确定性模拟。不是任意 task 的真实诊断能力。[6]

第一段：建立能共同检查的问题

用户：“检查这次 profile，先找一个值得验证的瓶颈。”任务携带运行和对象。Agent 先说明可用范围、指标口径和原始产物缺失，再进入分析。此时用户可以补充“我只关心本轮局部等待”，或要求补足更大范围数据。

第二段：把解释落回同一个现场

Agent 将首要假设指向同步释放与等待方的时间关系。用户点击“泳道”，查看同一 task 的 AIC producer、AIV peer 与同步事件，再返回原消息继续追问。设计意图是减少“我刚才看的那一段在哪里”的记忆负担。

此时不能因为图上存在等待就断言它可被删除。用户仍应能追问：它是否由必要依赖造成，是否与关键路径有关，还缺什么证据？

第三段：审批的是实验，而不是一句乐观判断

原型提案只改变“同步释放提前量”，展示影响范围、风险、验证指标和可撤销性。用户可以批准或拒绝；目标方案允许先修改提案再重新评审。真实工程接入时，这一步需要替换为有源码身份、实际补丁与执行计划的提案。

第四段：结果返回任务，同时保留尚未证明的部分

批准之后，原型显示后台进度并返回对照与结论。构造数据中局部关键区间由 12.769 μs 变为 11.890 μs；这个数值只说明模拟变换的输出。它不证明真实同步释放可被这样调整，也不证明真实算子或硬件获得收益。

本次故事的真正验收点是：用户是否知道依据来自哪次运行、是否认出同一对象、是否理解批准了什么，以及能否解释为什么局部变化还不能代表整体收益。[3][6][7]

08

从性能扩展到开发：复用判断机制，替换领域证据

以下三个场景基于既有用户故事重新展开，均是目标交互脚本，尚无对应的完整运行 Demo。

目标场景 A

编译失败：从“报错在哪”推进到“什么条件触发了失败”

触发：用户在某算子编译失败后，选择日志条目发起任务：“这个配置为什么编不过？”

  1. 建立复现条件：绑定源码、编译器版本、输入规格和编译参数；收集失败阶段与完整日志。不能仅凭最后一行错误定位根因。
  2. 并排检查证据：有对应产物时打开 Pass 前后图或 IR。Agent 解释观察到的变化，同时区分“错误暴露阶段”和“错误引入阶段”。
  3. 提出最小实验：保留原问题特征，缩小输入或配置。用户确认缩小后的用例仍代表原始失败，而不是新的问题。
  4. 评审候选修复：展示受影响代码与假设，执行重新编译；编译通过后继续跑语义和精度回归。

停止点：缺少前后产物时，可以解释日志和指导补采，不能虚构 Pass 变化。完成标准：原始复现通过，相关回归通过，并说明修复适用范围。[2][8]

目标场景 B

精度异常：先确认判定合理，再寻找最早可定位差异

触发：用户选中异常结果：“为什么这里与 golden 对不上？”

  1. 校验判定标准：确认输入、dtype、参考实现、误差阈值与可复现性。让用户确认业务可接受的精度范围，Agent 不应为了让测试变绿而自行放宽阈值。
  2. 缩小问题：按可用工具和产物定位较早的异常阶段或中间量。标出“首次观测到的差异”，不直接等同于已证明的根因。
  3. 组织竞争解释：计算路径、数据类型、实现公式或中间数据覆盖等都可能成为假设；只有得到对应证据时才进一步确认。
  4. 进行最小修复实验：用户检查修改后，先重跑原异常，再覆盖边界输入，最后重新评估性能代价。

能力限制：本次核验的 2.x 文档明确区分 Tensor Graph / Pass 检查与上板中间数据检查，并说明不支持自动进行 Pass 间对比。因此“Agent 自动找到所有阶段的首错”只能是待接入能力，不能写成现有工具保证。[9]

完成标准：在声明的输入集合和阈值下回归通过；若只是规避一个输入，应报告为局部绕行，不称为问题已彻底解决。

目标场景 C

新算子开发：先交付可信基线，再迭代性能版本

触发：用户提供参考计算：“把这段逻辑做成目标硬件上可验证的算子。”

  1. 澄清规格：确定算子边界、输入范围、动态 shape、dtype、精度和目标环境；把开放问题写进规格，而不是默认猜测。
  2. 检索可用能力：Agent 给出当前版本可用的 API 与示例来源。对不确定适配先做小验证；不会因为名字相似就假定行为相同。
  3. 生成基线：输出代码骨架、运行方式、golden 与验收样例。用户先评审语义，再授权构建与执行。
  4. 进入性能循环：正确性基线成立后采集性能，针对一个假设建立候选版本，并复用前述准入、定位、审批和比较机制。

完成标准：产物能在声明环境复现，通过约定样例；性能优化作为下一阶段独立验收。生成代码只是中间产物。[2][5][9][10]

四类任务共用什么，又分别需要什么

任务共同机制专用证据主要结果对象
性能诊断证据准入、对象保持、受控实验、结果范围时序、同步、计数器、可比 run实验与回归结论
编译问题同上，重点校验复现与版本编译日志、阶段产物、最小复现修复与复现包
精度问题同上，先约定判定标准golden、中间量、dtype、误差阈值差异定位与测试结果
新算子开发同上，先澄清任务边界参考语义、API 版本、样例、目标约束规格、基线代码与测试
09

交互原则：让停点、接管和恢复都可理解

体验应围绕用户当前要判断的事情组织；详细字段与原始产物可以按需展开。

9.1 专业画布服务当前判断

任务时间线保存目标、证据和决定；泳道、图、源码、diff 与 compare 从对应消息打开。默认先展示一个与当前问题相关的工作面，专家可展开更完整的原始证据。关闭画布后恢复原消息与对象，不要求用户重新描述刚才的发现。新手和专家共享同一证据来源，差异只是解释密度和默认展开程度。[1][2]

情境界面应表达用户下一步系统要保护的判断
证据不足缺哪些必需通道，当前不能回答什么补采、替换证据或缩小问题不能把缺失数据解释成没有瓶颈
对象不唯一候选实例、轮次与来源差异确认对象或补定位证据不能误把一个调用改成另一个
源码已变化当前源码与采集构建的差异重绑、重新采集或明确看历史证据不能套用过期修改与审批
两次运行不可比具体哪些条件不匹配；差值不展示分别查看或重新对齐实验不能把条件变化读成绩效
任务执行失败失败阶段、已完成动作、保留产物检查、重试或修改计划不能把部分执行写成完整成功
用户取消 / 会话恢复停止请求、确认状态与恢复后的实际进度保留结果、继续或结束不能重复运行或错误声明已停止

前四类状态来自 D3 契约，主路径与证据不足已在原稿走查实际走查，其余通过源码 guard 与契约核对。执行器的真实失败、取消确认和恢复行为属于本次工程方案，尚未连接后端。[3][6][7]

9.2 把中断当作一次任务内的决定

拒绝提案

保留原证据与判断，不发起复跑。用户可以说明拒绝原因，Agent 据此修改假设或缩小实验。拒绝之后不应强制重建任务。

更换对象或输入

明确区分“浏览新对象”和“将任务改为新对象”。后者生成新的上下文版本，重新检查证据和审批是否仍有效。

Agent 不可用

已有证据和任务结果继续可读；可运行的确定性工具仍可用。界面说明智能分析暂不可用，保留稍后继续的位置。

团队交接

交接目标、对象、证据快照、尝试过的实验及未解问题。接手者先检查记录，无需靠完整聊天文本猜测当前结论。

9.3 什么反馈最值得优先呈现

建议把“当前对象、正在做什么、何时需要我、能证明到哪里”置于主层；工具版本、raw IDs、调用输入与原始产物放入可展开详情。活动卡说明为什么调用某个能力、读了什么、产出了什么。采用这些原则，目的是让用户能审查工作，而不是迫使用户理解系统实现的每一个字段。

当前材料证明了研究问题与模拟交互存在；下一步要分别验证系统可执行性和用户判断收益。

当前层次已具备的证据仍不能据此声称

10.1 建议的验证顺序

  1. 把现有原型的判断语义测清楚。

    让目标用户完成准入、定位、审批与可比性解释任务，记录误判、回找和求助。优先修正会导致错误决策的界面表达。

  2. 接一条只读真实证据链。

    在明确的产品线、版本和样例上，接入真实 run 与对象解析；让结论能回投且缺口不被隐藏。以代表性反例验证保护规则。

  3. 接一轮真实受控实验。

    补源码 / 构建身份、隔离修改、实际执行与 paired collection；验证授权绑定、失败、取消、恢复和比较规则。取得真实可追溯结果后再谈性能收益。

  4. 扩展任务与团队复现。

    分别引入编译、精度、开发场景，扩展专用证据和验收标准。通过任务包和版本记录检查团队能否复跑，而非仅复述 Agent 的建议。

10.2 用行为与判断质量评估设计

验证任务观察指标（待采集）需要区分的结果
判断证据是否足够不受支持结论的接受率；是否选对补采动作看懂状态标签 vs 真正知道判断边界
找出建议指向的对象对象识别正确率；回找次数；上下文丢失跳转成功 vs 命中正确实例 / 源码
评审一次候选实验能否复述改动、风险和验证条件；错误批准情况点了批准 vs 理解授权范围
解释复跑结果可比性判断正确率；局部收益外推错误看见绿色结果 vs 理解适用范围
恢复或交接任务恢复后状态一致性；重复执行；复现成功情况聊天仍在 vs 工作可继续

用户研究可采用同类任务与当前工作方式对比，记录用户经验和任务难度；重复任务要处理学习效应。工程验证则应检查状态不变式和真实产物。两类结果分别报告，不用“原型流程走通”替代用户测试，也不预设提升百分比。

待验证的设计价值：让 Toolkit 成为 Agent 的性能证据环境。专业对象、证据范围与验证条件可被共享之后，用户有望减少上下文拼接，更有依据地选择实验，并更准确地判断结果。

最终需要由真实任务、用户行为与执行证据共同支持。[1]
